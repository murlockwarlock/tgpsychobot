# DATA, обработчики событий и догоняющие сообщения

## Что это решает

Модель отвечает пользователю обычным текстом и при необходимости добавляет в конце один служебный блок `<DATA>`. Пользователь этот блок не видит. Код разбирает JSON один раз и получает из него:

- текущее состояние алгоритма;
- одноразовые события;
- метаданные, которые нужно сохранить.

Это один механизм для обычного диалога, темы, психологического алгоритма и результата теста. Отдельный формат для тестов или воронок не нужен.

## Формат DATA

```text
<DATA>
{
  "current_state": {
    "current_step": "STAGE_1_HOBBY"
  },
  "events": ["HOBBY_RECEIVED"],
  "save_mode": "merge",
  "metadata": {
    "interests": ["играть в компьютер"]
  }
}
</DATA>
```

Правила:

1. Для промптов используйте один блок в самом конце ответа. Технически парсер найдёт его в любом месте текста, но конец — стабильное соглашение для модели.
2. Внутри находится только валидный JSON. Markdown, комментарии и кодовые кавычки вокруг JSON не нужны.
3. `current_state` хранит состояние алгоритма. Название текущего этапа всегда лежит в `current_state.current_step`.
4. `events` содержит события именно этого ответа. Модель не должна повторять событие без нового основания.
5. `metadata` содержит факты, которые нужно сохранить.
6. `save_mode: "merge"` объединяет новые метаданные с текущими. Вложенные объекты также объединяются.
7. `save_mode: "snapshot"` создаёт отдельный снимок и не меняет объединённые метаданные текущего состояния.

Необязательные пустые разделы можно не передавать. Старый `[DATA]...[/DATA]` читается для старых промптов, но новые промпты надо писать только с `<DATA>`.

## Где хранятся данные

Рабочая область определяется ключом:

```text
user_id + dialogue_id + topic_id
```

Основной диалог хранится как `topic_id = 0`. У каждой темы своё состояние. Новый диалог создаёт новое состояние. Если пользователь вернулся в прежнюю тему внутри того же диалога, работа продолжается с её предыдущими данными.

Перед следующим запросом модели код передаёт сохранённое состояние этой области отдельным служебным сообщением. Основной системный промпт остаётся неизменным между пользователями, поэтому его можно кешировать у провайдера.

## Как использовать в промпте

Приложение умеет разобрать `<DATA>`, но не добавляет модели правила протокола автоматически. Если сценарий должен сохранять этапы, события или метаданные, формат и контракты нужно явно описать в системном промпте.

Пример:

```text
Сначала спроси пользователя об интересах.
После содержательного ответа:
- перейди на этап STAGE_2_GOAL;
- создай событие HOBBY_RECEIVED;
- сохрани интересы в metadata.interests.
Не создавай HOBBY_RECEIVED повторно, если пользователь просто уточняет прежний ответ.
```

Для теста используется тот же формат. Пример требования в промпте результата:

```text
После готовой интерпретации установи current_step = TEST_RESULT_READY,
создай событие TEST_COMPLETED и сохрани рассчитанные показатели в metadata.test.
```

## Статистика этапов

Переход записывается, только когда значение `current_state.current_step` изменилось. Если модель несколько раз вернула один этап подряд, это один вход в этап, а не несколько.

В админке показывается:

- сколько уникальных пользователей вошло в этап;
- сколько всего было переходов в этап;
- сколько уникальных пользователей сейчас находится на этапе.

Этапы выводятся постранично. Кнопка с названием этапа открывает список пользователей: имя, username, Telegram ID, число входов, время последнего входа и отметку о том, что пользователь сейчас находится на этом этапе. В списке по 10 пользователей на страницу.

Открыть статистику можно двумя способами:

- `Админ-панель → Автоматизации → Статистика этапов` — общая статистика;
- `Админ-панель → Темы → нужная тема → Статистика этапов` — только выбранная тема.

В обычной статистике бота есть короткая сводка: сколько пользователей проходили этапы, сколько находятся на них сейчас и сколько переходов зафиксировано. Кнопка «Подробно по этапам» открывает полный экран и возвращает обратно в общую статистику.

## Обработчики событий

Один обработчик состоит из области, условий и действий.

Область:

- основной диалог;
- одна или несколько выбранных тем;
- все темы, включая будущие.

Условия:

- имя события;
- текущий этап;
- значение по пути в метаданных.

Все условия одного обработчика должны совпасть одновременно. Это AND. OR отдельным переключателем не используется: для альтернативных вариантов создаются два обработчика с одинаковыми действиями.

Действия выполняются по порядку:

- отправить сообщение всем администраторам;
- отправить сообщение выбранному Telegram ID;
- сохранить дополнительные метаданные.

В шаблоне сообщения доступны:

```text
{event}
{current_step}
{user_id}
{username}
{name}
{dialogue_id}
{topic_id}
{metadata.profile.phone}
```

Последний вариант читает любое вложенное поле из `metadata`.

Обработчик создаётся выключенным. Перед включением надо выбрать область, добавить хотя бы одно условие и хотя бы одно действие. Каждое успешно выполненное действие фиксируется отдельно и не повторяется для того же события. Если действие упало, событие остаётся в очереди и будет повторено. Очередь проверяется раз в минуту.

Настройка:

- глобально: `Админ-панель → Автоматизации → Обработчики событий`;
- внутри темы: `Админ-панель → Темы → нужная тема → Обработчики событий`.

При создании из темы обработчик сразу привязывается к ней. Кнопка «Отвязать» убирает только связь с темой. Сам обработчик остаётся и удаляется только из его карточки.

## Догоняющие сообщения

Цепочка запускается после реального сообщения или нажатия кнопки пользователем. Действия администратора в админке таймер не запускают.

Для цепочки настраиваются:

- основной диалог, выбранные темы или все темы;
- один или несколько шагов;
- задержка каждого шага в минутах;
- обычный текст или инструкция для генерации через AI;
- тихие часы и часовой пояс;
- случайная добавка к задержке.

Первый шаг отсчитывается от последней активности пользователя. Следующие шаги — от предыдущей отправки. Новая активность начинает цепочку с первого шага заново. Смена темы или создание нового диалога отменяет старую цепочку для прежней области.

AI-шаг получает промпт активного диалога, историю в пределах настроенного контекста, служебные данные текущего пользователя и отдельную инструкцию с пометкой о паузе пользователя. Отправленный AI-текст сохраняется в историю диалога. Служебные данные из ответа follow-up не применяются: догоняющее сообщение не должно само менять этап или создавать событие.

Вызов follow-up помечается типом `followup` в общем журнале AI-запросов. В админке его можно отдельно отфильтровать от обычных AI-вызовов.

Цепочка создаётся выключенной. Включить её можно после выбора области и добавления хотя бы одного шага. Планировщик проверяет готовые к отправке шаги раз в минуту. Повторная отправка одного шага в рамках одного запуска защищена уникальной записью доставки.

Настройка:

- глобально: `Админ-панель → Автоматизации → Догоняющие сообщения`;
- внутри темы: `Админ-панель → Темы → нужная тема → Догоняющие сообщения`.

## Общие настройки и тесты

Сбор имени, пола и возраста относится ко всему боту:

```text
Админ-панель → Общие настройки
```

Если поле уже заполнено, бот повторно его не спрашивает. Настройки самого теста, его вопросы, формулы, отдельный промпт результата и режим передачи переменных находятся в `Управлении тестом`.

`<DATA>` работает в Telegram при отдельной генерации результата теста и при передаче результата в основной диалог. Статистика этапов теста строится тем же способом — по сменам `current_step`.

MAX использует отдельные обработчики сообщений. Наличие общих таблиц в БД само по себе не подключает новый парсер к MAX: перенос Telegram-логики туда должен выполняться и тестироваться отдельно.

## Создание отдельной копии бота

Для каждой копии нужны отдельные:

- токен Telegram;
- PostgreSQL-база;
- имя процесса PM2;
- порт приложения;
- webhook-префикс, даже если сейчас используется polling;
- список владельцев в `OWNER_IDS`.

Секреты не записываются в Git и PM2-конфиг. В конфиге используются имена переменных окружения:

```javascript
BOT_TOKEN: process.env.MY_BOT_TOKEN
DATABASE_URL: process.env.MY_BOT_DATABASE_URL
OWNER_IDS: process.env.MY_BOT_OWNER_IDS
```

Для `psy5d_fulltest` используется `ecosystem.fulltest.config.js`. Запуск только этой копии:

```bash
PROD_PM2_NAMES=psy5d_fulltest \
PROD_PM2_CONFIG=ecosystem.fulltest.config.js \
bash deploy_prod.sh
```

Перед запуском надо проверить, что порт не занят другим PM2-процессом, токен не используется другим webhook/polling-процессом, база действительно отдельная, а `OWNER_IDS` содержит только нужных владельцев.

## Проверка после изменений

Минимальный прогон:

1. Обычный диалог без `<DATA>` — ответ не меняется.
2. Валидный `<DATA>` — XML не виден пользователю, состояние и метаданные сохранены.
3. Невалидный JSON — видимый ответ не ломается, служебный блок не применяется, ошибка попадает в лог.
4. `merge` — вложенные данные объединяются.
5. `snapshot` — создаётся отдельная запись без изменения объединённого состояния.
6. Одинаковый `current_step` два раза — второй переход не создаётся.
7. Разные темы и диалоги — состояния не смешиваются.
8. Событие с совпавшими условиями — все действия выполнены один раз.
9. Событие с несовпавшим условием — действия не выполнены.
10. Обычный и AI-шаг догоняющей цепочки, тихие часы, новая активность и смена темы.
11. Основной и отдельный промпт результата теста с `<DATA>`.
12. Полный набор автоматических тестов: `pytest -q`.
